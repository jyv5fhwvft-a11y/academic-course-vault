Lecture 18: Inode Architecture & File System Layouts Summary

1. Objective

Calculate maximum file scale size capacities for an inode architecture layout featuring direct, single indirect, and double indirect block pointers.

2. Prerequisites

L17 (File Abstraction & Directory Topology), bit-to-byte storage math.

3 & 4. Pedagogical Analogies

Analogy 1 (Everyday Life): The Library Ledger Card vs. The Book Content
Imagine checking out a book from a library. The book text itself represents the real data blocks. The library index filing card taped inside the front cover is the Inode. The card doesn't contain any story lines; instead, it holds the metadata details: who owns the book (Owner ID), who is allowed to read it (Permissions), the exact character length (File Size), and a list of shelf coordinate numbers telling you exactly where the chapters are stored on the library floor (Block Pointers). If a book grows too long, the card lists a coordinate to another ledger box containing additional lists of shelf coordinates (Indirect Pointers).

Analogy 2 (Pure Technical): An Index Allocation Array with Indirect Node Chains
An inode layout operates identically to a multi-tiered array indexing system, where static top-level row keys reference raw data blocks, while overflow indices point to sub-arrays of secondary pointers.

5. System Cohesion Matrix

• Relies On: Module 3 (Memory Management) — Connects to virtual memory systems to implement Memory Mapping (mmap), which maps a file's disk block inode indexes directly into a thread's virtual page frames.
• Feeds Into: L19 (Crash Consistency) — Any modification to file text or directory sizing metrics requires executing atomic metadata pointer updates across the inode map.

6. Core Breakdown

Unix-like systems separate a file's human-readable name from its core metadata. An Inode (Index Node) is a fixed-size kernel data structure dedicated to a single file instance. It stores metadata metrics: File Type, Size, Owner, Access Permissions, Timestamps, and a critical index tracking array called Block Pointers.

To keep the inode size small while supporting massive files, the layout utilizes an asymmetric branching index tree structure. It provides a row of Direct Pointers that map straight to data sectors, a Single Indirect Pointer (pointing to a disk block filled with pointers to data), and a Double Indirect Pointer (pointing to a block of pointers to blocks of pointers) to handle large file sizes.

7. Lexicon / Terms

• Inode: The foundational data structure in Unix file systems tracking a single file's complete metadata metrics and physical disk block locations.
• Direct Pointer: An internal inode array address slot that points directly to a real physical block holding file data bytes.
• Indirect Pointer: An array slot inside an inode that points to a sector block allocated exclusively to hold additional address tracking pointers.
• Metadata: Structural descriptive data about a file (permissions, sizing, timestamps) rather than the literal file contents.

8. Practical Example: Inode Storage Capacity Calculation Math

Workload Vector Constraints: 12 Direct Pointers, 1 Single Indirect, 1 Double Indirect. System block size = 4KB (4096 bytes); disk pointer address = 4 bytes.

------------------------------------------------================= Step 1: Calculate Direct Block capacity. 12 blocks * 4KB = 48 KB Step 2: Calculate Single Indirect capacity. One 4KB block holds: 4096 bytes / 4 bytes per pointer = 1024 pointer addresses. 1024 pointers * 4KB block size = 4096 KB = 4 MB Step 3: Calculate Double Indirect capacity. Addresses branch exponentially: 1024 * 1024 = 1,048,576 pointers. 1,048,576 pointers * 4KB block size = 4,194,304 KB = 4 GB Step 4: Sum the branches. Maximum Size Limit = 48 KB + 4 MB + 4 GB = 4.004 GB ------------------------------------------------=================

This calculation highlights how asymmetric pointer indexing scales capacity boundaries up exponentially to hold large file assets without bloating individual inode space overhead metrics.

9. Interactive Classroom Activity

The Live Inode Inspection Hunt: Open up a live Linux terminal environment via projector. Instruct students to run the system command ls -i or stat resume.pdf. Point out the integer index value displayed at the start of the print line. Show the class how creating hard links duplicates this exact same numeric key across different directory trees, proving that multiple names can mask a single physical inode core.
