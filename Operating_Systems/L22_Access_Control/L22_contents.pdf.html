Lecture 22: Access Control Summary

1. Objective

Apply an access control matrix and distinguish an Access Control List (ACL) from a capability token.

2. Prerequisites

Module 5 (L17: File Abstraction & Directory Topology).

3 & 4. Pedagogical Analogies

Analogy 1 (Everyday Life): The Hotel Room Ledger vs. The Physical Room Key
Imagine a hotel security framework. One design approach checks an explicit sheet clipped right onto the door frame: "Who is allowed into Room 204?" (ACL, resource-centric). Another design completely ignores the doors and hands you an electronic keycard token that simply works instantly on whichever lock it fits (Capability, user-centric).

Analogy 2 (Pure Technical): Stateless Network File System Mounting Rules vs. Cryptographic JWT Bearer Tokens
An ACL acts like a firewall rule table mapped directly onto a disk block node, while a capability behaves like an unforgeable, kernel-signed memory address descriptor held by a running thread.

5. System Cohesion Matrix

• Relies On: Module 1 (L02: Dual-Mode Barrier) — Relies on Ring 0 isolation to guarantee that user-space processes cannot modify their own capability tokens or rewrite resource security bits.
• Feeds Into: L23 (Authentication) — Access control lists only work if the system possesses an unshakeable mechanism to verify the identity of the user calling them.

6. Core Breakdown

An operating system manages file security using Protection Domains. This architecture is mathematically mapped using an Access Control Matrix, where rows represent subjects and columns represent resource objects.

Because matrices are massive and sparse, production kernels use two opposing bookkeeping methodologies: ACLs decompose the matrix by columns, attaching a strict authorization list directly to the resource itself. Capabilities decompose the matrix by rows, handing secure, unforgeable tokens directly to the user or process context.

7. Lexicon / Terms

• Access Control Matrix: A conceptual grid mapping user domains against system objects to define structural read, write, and execute permissions.
• ACL (Access Control List): A column-oriented optimization where resource permissions are tracked directly on the asset container.
• Capability: A row-oriented security optimization where unforgeable access tokens are carried and presented by the active user process.
• Protection Domain: The bounded environment profile determining which operations a thread is permitted to execute across various system objects.

8. Practical Example: Linux Standard File Permission Vector

Standard Unix file systems compact ACL architecture down to 9 simple permission bits matching Owner, Group, and Others fields:

------------------------------------------------================= Permission String Example: rwxr-xr-- Isolate the bit segments: 1. Owner Bits: 'rwx' ➔ Owner can Read, Write, and Execute. 2. Group Bits: 'r-x' ➔ Group members can Read and Execute, but cannot modify. 3. Other Bits: 'r--' ➔ All external system callers can strictly Read. Conclusion: Core protection domains block illegal mutation paths out-of-the-box. ------------------------------------------------=================

9. Interactive Classroom Activity

The Matrix Verification Challenge: Sketch a 4x4 Access Control Matrix on the chalkboard listing users (Alice, Bob, Charlie) and resources (file1.txt, /dev/tty0). Rapidly shout out target scenarios: "Can Bob write to file1?" or "Can Charlie execute /dev/tty0?" Have students call out answers directly from the grid lines to practice reading sparse matrix definitions.
