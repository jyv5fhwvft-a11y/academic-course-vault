Lecture 14: Race Conditions & Mutual Exclusion Summary

1. Objective

Identify a data race condition inside a multi-threaded code block and refactor the code to guarantee mutual exclusion using a POSIX mutex lock.

2. Prerequisites

Module 3 (All Lectures), L09 (Threads & Concurrency).

3 & 4. Pedagogical Analogies

Analogy 1 (Everyday Life): The Shared Digital Piggy Bank
Imagine a digital piggy bank shared between two siblings (Threads) who can both add money at the same time. The bank currently holds $100. Siblings A and B both want to add $1 at the exact same instant. Sibling A reads the balance ($100). Right before Sibling A can write down $101, Sibling B barges in, reads the balance ($100), and writes down $101. Sibling A then finishes their turn and writes down $101. Even though two separate dollars were added, the bank ends up short because one update overwrote the other. This is a Race Condition. To fix it, we introduce a Mutex Lock—a single physical bathroom key taped to the bank. A sibling must grab the key, lock the room, change the balance in total isolation, and return the key.

Analogy 2 (Pure Technical): A Transactional Database Table Row Lock
A software mutex lock behaves identically to a hardware-enforced write-reservation token that blocks out raw processor access lines to a specific memory array address index until a commit sequence resolves.

5. System Cohesion Matrix

• Relies On: Module 3 (Memory Management) — Requires threads pointing to identical shared virtual memory page coordinates to manifest a race state.
• Feeds Into: L15 (Classic Problems & Deadlocks) — Introducing multiple independent mutex locks to protect complex data structures creates the precise architectural prerequisites for deadlock loops.

6. Core Breakdown

When multiple concurrent execution contexts read and modify a shared variable simultaneously, the final outcome depends entirely on the unpredictable order in which the instruction lines interleave. This vulnerability is a Race Condition, and the specific block of code executing the modification is the Critical Section.

To prevent corruption, we must enforce Mutual Exclusion—guaranteeing that only one thread can sit inside the critical section at any given time. This requires an atomic hardware instruction (like Test-and-Set or Compare-and-Swap) to verify and flip a Mutex flag in a single clock cycle without interruption.

7. Lexicon / Terms

• Race Condition: A concurrency bug where the system output shifts nondeterministically based on the precise timing and execution order of overlapping threads.
• Critical Section: A structural window of source code that reads or writes to a shared, mutable global or heap state resource.
• Mutual Exclusion (Mutex): A synchronization primitive that locks out concurrent access, ensuring only one execution thread can claim a resource slot.
• Atomic Operation: A low-level processor instruction sequence that executes completely to completion as a single indivisible unit without any possibility of preemption.

8. Practical Example

#include <pthread.h> #include <stdio.h> int shared_balance = 100; // Shared resource in the data segment pthread_mutex_t bank_lock = PTHREAD_MUTEX_INITIALIZER; // The Mutex Primitive void* add_dollar_routine(void* arg) { for(int i = 0; i < 10000; i++) { pthread_mutex_lock(&bank_lock); // Acquire exclusive access / entry path // --- START CRITICAL SECTION --- shared_balance++; // Shared state modification block // ---- END CRITICAL SECTION ---- pthread_mutex_unlock(&bank_lock); // Release lock / exit path } return NULL; } int main() { pthread_t t1, t2; pthread_create(&t1, NULL, add_dollar_routine, NULL); pthread_create(&t2, NULL, add_dollar_routine, NULL); pthread_join(t1, NULL); pthread_join(t2, NULL); printf("Final absolute guaranteed balance: $%d\n", shared_balance); // Always 20100 return 0; }

9. Interactive Classroom Activity

The Shared Whiteboard Disruption: Draw a large single number "0" on the center classroom whiteboard. Appoint two students to act as Threads. Instruct them that their only loop instruction is to read the board number, add 1 in their head, and write the new value over the old one. Have them both try to do this simultaneously as fast as possible with different colored markers. Watch how their writing overrides each other, leading to a corrupt, incorrect math total on the board, demonstrating a real data race.
